### A4 · roles / types 是否合官网口径 —— ✅ 成立，但官网对 3 位新英雄自相矛盾

**硬证据 1（types 与官网数字职业码 1:1）**：官网 `herolist.json` 带 `hero_type` / `hero_type2`（数字）。用 `1=战士 2=法师 3=坦克 4=刺客 5=射手 6=辅助` 展开后与 `heroes.js` 的 `types` 比对：

```
heroes where local types != official hero_type/hero_type2 mapping: 0
hero_type histogram: {1:31, 2:29, 3:12, 4:18, 5:21, 6:22} ; hero_type2 present: 51
```

这个映射本身也由官网列表页内联的筛选器佐证：`data-type="3"→坦克`、`1→战士`、`4→刺客`、`2→法师`、`5→射手`、`6→辅助`（我在 `herolist.shtml` 原文里逐条抓到了 `<li data-type="N"><label>中文</label>`）。

**硬证据 2（roles 的数字串解码）**：官网 `herolist.json` 每条都有 `"roles": "1|5"` 这类数字串（133/133 条都有）。用 `1=对抗路 2=打野 3=中路 4=发育路 5=游走` 解码后与本地 `roles` 比对：

```
heroes where local roles != ROLE_MAP[official roles]: 0   (133/133)
digit 1 -> 对抗路 44 位（廉颇/白起/吕布/关羽…）
digit 2 -> 打野   50 位（赵云/阿轲/孙悟空/李白…）
digit 3 -> 中路   31 位（小乔/妲己/嬴政/貂蝉…）
digit 4 -> 发育路 20 位（孙尚香/鲁班七号/马可波罗/公孙离…）
digit 5 -> 游走   34 位（庄周/刘禅/孙膑/牛魔…）
```

**硬证据 3（用官网另一个数据源交叉验证中文口径）**：官网资料库接口 `https://pvp.qq.com/zlkdatasys/heroskinlist.json`（HTTP 200 / 797132 B）里 `fllb_2105` 字段是中文分路文案。逐条比对：

```
heroes whose fllb_2105 is a pure lane string: 130
  identical order: 130   same set different order: 0   DIFFERENT lane set: 0
not-a-lane (3): 心魔六耳(549) fllb_2105="" ; 卢雅那(547) fllb_2105="射手" ; 王维(138) fllb_2105="法师"
```

**结论**：`roles` 用「游走」而不是「辅助」——与官网口径一致（`types` 里才用「辅助」），这一点成立。**唯一保留意见**：王维 / 卢雅那 / 心魔六耳这 3 位（都是最新的英雄）在官网资料库里该字段填的是职业名或空，所以这 3 位的分路只有 `herolist.json` 的数字串单一来源，无法交叉证实。

## 2. BP 规则正确性（B 组）

我用**真实 133 英雄数据**（不是 lead 自检里的假数据）在 Node vm 里跑了自己的断言，并把真实 DOM 也跑了一遍（第 3 节）。

### B5 · 三赛制顺序 —— ✅ 与各自声明一致

```
ranked: steps=16  每侧 bans={blue:3,red:3}  picks={blue:5,red:5}
   实测序列: Bb,Rb,Rb,Bb,Bb,Rb, Bp,Rp,Rp,Bp,Bp,Rp,Rp,Bp,Bp,Rp   ← 蓝1→红2→蓝2→红1 ban，之后蓝红交替 10 pick ✅
kpl   : steps=20  每侧 bans={blue:5,red:5}  picks={blue:5,red:5}
   实测序列: Bb,Rb,Rb,Bb,Bb,Rb, Bp,Rp,Rp,Bp,Bp,Rp, Rb,Bb,Bb,Rb, Bp,Rp,Rp,Bp   ✅
peak  : steps=11  每侧 bans={blue:3,red:3}  picks={blue:5,red:5}
   第 1 步是 {s:'both', a:'ban', n:3}：双方各 3 手、都出满才 step+=1，随后 10 手 pick（最后一位是红方五楼）✅
```

- **ranked** 的 ban 顺序「蓝1红2蓝2红1」= `B,R,R,B,B,R`，与游戏内征召一致；pick 顺序 `B,R,R,B,B,R,R,B,B,R` 也正确。
- **KPL** 10 ban（首轮 3+3、次轮 2+2）+ 10 pick → 20 步，与 README 表格一致；第二轮 ban 采纳「红→蓝→蓝→红」，README 已声明这是本项目自选顺序（各赛事有差异），**与我独立判断的「符合其自身声明」一致**。
- **peak（巅峰赛）**：早期版本这里是**坏的**（详见第 6 节「过程中已修复」），当前版本语义正确：`step` 在同步 ban 阶段保持 0、`stepDone` 记录各方已出手次数、蓝方连出第 4 手会被拒（`蓝方本步已经出满 3 手`）。

### B6 · 边界与异常 —— ✅ 全部安全

- 打满整局后再操作 → `{ok:false, reason:'本轮 BP 已结束'}`；
- 重复英雄 / 不存在英雄 / `null` → 全部拒绝并给出中文原因；
- 一路撤销到底 → step=0、可选池恢复 133；到底后再撤销 → 拒绝；
- 撤销后执行新动作 → `canRedo=false`（重做链被截断）；
- 切换赛制 → 旧状态不残留；`reset()` 保留赛制、清空步骤；
- 巅峰赛同步步骤里同侧超出手数 → 拒绝；侧别 ban 位容量上限校验生效。

**畸形导入（9 类，每种都断言「拒绝 + 当前 BP 一字节没动」）**：

```

empty object  -> ok=false reason="文件里没有任何 BP 数据"    currentBPuntouched=true
bare array    -> ok=false reason="数据格式错误"              currentBPuntouched=true
empty actions -> ok=false reason="文件里没有任何 BP 数据"    currentBPuntouched=true
empty bans/picks -> ok=false reason="文件里没有任何 BP 数据" currentBPuntouched=true
foreign app   -> ok=false reason="不是本站导出的 BP 文件"    currentBPuntouched=true
garbage actions('nope') -> ok=false                          currentBPuntouched=true
null / string -> ok=false reason="数据格式错误"              currentBPuntouched=true
```

**合法数据没有被误拒**（这是我最担心的「校验过头」）：自己导出的 JSON → `applied=16` ✅；自己的分享码 → step 16 ✅；`{bans,picks}` 简化格式 → `applied=6` ✅；最小 actions 载荷 → `applied=2` ✅。

### B7 · 导出 → 导入 round-trip —— ✅ 三种赛制全部无损

对 ranked / kpl / peak 各自打满整局后：导出 → 切到别的赛制 → 导入，比对 `step / bans / picks / stepSides / done`，**全部一致，`skipped=0`**。分享码（URL hash）单独再验一遍，同样一致。

### B8 · 导出里每一步的 `side` 是否真实 —— ✅

三种赛制的导出 `side` 序列都与 steps 表逐步对齐。特别验了巅峰赛的**反序**场景（红方先 ban 3 手、蓝方后 ban 3 手）：导出的 `blue:*` 动作携带的确实是蓝方的 id、`red:*` 携带红方的 id，重新导入后双方 ban 列表完全还原。**没有把两侧 ban 混进同一列表的情况。**

### 当前版本仍存在的问题

#### 缺陷 1（高）· 键盘快捷键被绑定两次，`Ctrl+Z` 一次撤两步、`空格` 与 `Ctrl+B` 完全失效

**根因（代码级）**：`js/main.js` 里 `bindKeys()` 与 `draft.on(onDraftChange)` **各被调用两次**——`startAsConsole()`（第 69/70 行）调一次，`app.start()` 在其后又调一次（第 56/57 行）。于是 `document` 上挂了两个 keydown 监听器。

**复现与证据**（在页面里包一层 `WZ.draft.undo/redo` 统计调用次数）：

```
6 步状态下按一次 Ctrl+Z: {"step":4,"calls":["undo","undo"]}      ← 期望 step 5 / 只调一次
按一次 Ctrl+Y          : {"calls":["redo","redo"]}
按一次 Ctrl+B          : boss false → false（切换两次等于没切）
按一次 空格            : {"btn":"开始","left":"01:00"}            ← 先 start 再 stop，表根本没走
按一次 "/"             : activeElement=searchInput ✅（幂等，唯一没坏的）
一次 BP 动作           : board.render 调用 2 次、sync.post 广播 2 次
```

**影响**：README「快捷键」表里 6 条有 3 条不对——**「空格」和「Ctrl+B」完全失效**，**Ctrl+Z / Ctrl+Y 每次执行两步**（属于会误伤直播数据的行为：选错一步按一下，实际退了两步）；只有 `/`、`Enter`、`Esc` 正常（Esc 因为带 `contains('boss')` 判断所以侥幸没坏）。此外每次 BP 动作会**渲染两遍、广播两遍**，属于无谓开销。

**建议修法**：删掉 `startAsConsole()` 里的 `bindKeys()` / `draft.on(onDraftChange)`（保留 `app.start()` 里的那对），或者在 `bindKeys`/`on` 里加去重标记。

#### 缺陷 2（中）· 展示窗的展示板底部超出视口 ~21px，「重新适配」按钮无效

**证据**（`?wzrole=display` 窗口，逐一设置视口尺寸后测量）：

```
1920x1080: flagH=39 stageY=39 stageCH=1080 scale=1.16  frameH=1044 frameBottom=1101 overflow=+21px
1600x900 : flagH=39 stageY=39 stageCH=900  scale=0.96  frameH=864  frameBottom=921  overflow=+21px
1366x768 : flagH=39 stageY=39 stageCH=768  scale=0.813 frameH=732  frameBottom=789  overflow=+21px
1280x720 : flagH=39 stageY=39 stageCH=720  scale=0.76  frameH=684  frameBottom=741  overflow=+21px
1440x900 : overflow=-15px（宽度成为约束时无溢出）
1024x768 : overflow=-66px
点「重新适配」后 1280x720: scale 仍 0.76 / overflow 仍 +21px   ← 按钮救不回来
```

**根因**：`board.fit()` 用 `stage.clientHeight`（=100vh）算可用高度、只扣 `2×18` padding，**没有扣掉它上方 39px 的 `#displayFlag` 提示条**；而 `body.role-display{overflow:hidden}` 又把溢出部分藏起来。由于高度约束在常见 16:9 比例下总是生效，**1600×900 / 1920×1080 / 1366×768 / 1280×720 这些直播常用尺寸都稳定溢出 21px**，展示板底部状态条（剩余可选 / ban-pick 计数 / 数据日期）会缺一截。

**建议修法**：`fit()` 改成用 `document.documentElement.clientHeight - stage.getBoundingClientRect().top - padY*2` 作为 `availH`（或显式减去 `#displayFlag` 的高度）。

#### 缺陷 3（中低）· 首次截图可能永久挂起，且展示板状态条卡在「正在生成截图…」

在**两次独立的完整回归**里观察到（合计约 13 次截图调用中有 4 次未出图）：点击「截图」后 `window.html2canvas(...)` 的 Promise **既不 resolve 也不 reject**，于是没有下载、没有报错、`#boardStatus` 永远停在「正在生成截图…」（toast 也停在同一条）。我随后专门写探针连跑 6 次（3 次被裁切场景 + 3 次直播模式）**6/6 都正常出图**，所以确认是间歇性的、不是必现：

```
[t2b 失败样本] diag: {"pending":null,"dlseen":[],"perr":null}  shot: null
              boardStatus: "正在生成截图…"（90 秒后仍未变化）
[shot-flake 探针] SUMMARY: runs=6 produced-PNG=6 STUCK=0
```

**影响**：偶发；但一旦发生，**「正在生成截图…」会留在展示板状态条上**——这是 OBS 画面的一部分，等于把调试文案播出去，且用户会以为截图成功了。**建议**：给 `html2canvas` 加超时看门狗（比如 15s 未结算就恢复状态条并提示失败）；至少保证状态条一定会被还原。

#### 缺陷 4（低）· 中央大图存在竞态，快速连续操作时会停在旧的一手

`board.showHero()` 用 `new Image()` 预加载、在 `onload/onerror` 里切图，但**没有「谁最新」的序号判断**，回调乱序落地时旧的一手会覆盖新的一手：

```
人工节奏（1.2s/手，连做 9 手）: 每一手中央大图都正确 ✅（廉颇→小乔→…→庄周）
同一 tick 内连做 8 手          : stage=小乔，期望=嬴政 ❌（4 秒后仍未自愈）
每手间隔 250ms 连做 8 手       : stage=鲁班七号，期望=鲁班七号 ✅
```

状态、ban 位、选手位、状态条**都是对的**，只有中央大图会旧；下一次动作会自愈。人类正常点击节奏下不会碰到，但「双窗口展示 + 脚本/快速连点」时有概率出现。**建议**：给 `showHero` 加一个自增 token，回调里 `if (token !== latest) return;`。

#### 缺陷 5（低）· README 里展示窗提示条的高度写作约 30px，实测 39px

`README` 第 74 行「建议裁剪掉顶部那条提示（约 30px）」，我实测 `#displayFlag` 高度 = **39px**（1920×1080 / 1600×900 / 1366×768 / 1280×720 均为 39）。影响很小（裁剪多点少点都能用），但数字应当对齐，否则用户裁不干净会留下一条边。

#### 缺陷 6（提示，非缺陷）· 3 位新英雄的 `splash` 为空

王维(138) / 大禹(188) / 卢雅那(547) 的官方大图本身就是 404，数据层正确地把 `splash` 置空、界面用首字兜底块降级——**这是正确处理，不是 bug**，README 也写明了。仅提示：这 3 位英雄在展示板上不会有中央大图。

## 7. 我如何质疑 lead 的自检（自检盲区）

lead 的自检我没有当证据用，只跑了一次做交叉参考：`node scripts/verify-engine.mjs` → **131 通过 / 0 失败**（在快照副本里跑，不污染工作区）。它的盲区（我这几轮实测到的）：

1. **原版 `verify-engine.mjs` 完全没覆盖 `peak` 赛制** —— 这正是巅峰赛带 3 个缺陷上线的原因（我第一轮读代码时就发现 peak 只有 1 个 `both` ban 步、红方只有 4 pick）。
2. **原版没覆盖「渲染层」**：KPL 每侧 5 个 ban 位却只建 4 个槽，纯引擎断言永远发现不了 —— 必须开浏览器数 DOM。
3. **原版没覆盖「持久化路径」**：`step===0 ⇒ 删草稿` 这种门控只有把 `main.js` 的执行路径和 localStorage 一起测才会暴露（我上一轮就是这样抓到巅峰赛刷新丢数据）。
4. **原版没覆盖畸形导入对「当前 BP」的副作用**：只断言「不崩」不够，要断言「拒绝后当前 BP 一字节没动」。
5. **`_smoke.js` 是注入式 DOM 断言**，天然测不到真实按键（`document.dispatchEvent` 会绕过浏览器默认行为）、测不到 html2canvas 的真实像素、也测不到 localStorage 跨刷新 —— 这些都必须用 CDP + 真 profile + 真像素。
6. lead 一度写进报告的「板子被裁则截图空白」结论**实测不成立**（我已用像素统计证伪，lead 也已撤回）——说明自检里的对照实验设计有缺陷（没有排除「跨域图没画进去」以外的变量）。
7. 用户自己的「截图真出图」自检若只查 `html2canvas` 是否 resolve，就会漏掉缺陷 3 的挂起分支（既不 resolve 也不 reject）。

## 8. 覆盖盲区（我没验证到的）

诚实列出，以下**不能算通过**：

1. **非 Chrome 浏览器**：全部浏览器测试只在 Chrome 153 headless 上做的。**Firefox / Safari / Edge 未验证**。特别地，README 关于「`file://` 同目录同源、BroadcastChannel + storage 可用」的说法是 **Chrome 行为**；Firefox 对 `file://` 的源处理不同，多窗口同步与 localStorage 可能表现不一样。**这是最大的盲区。**
2. **真实桌面「双击 index.html」**：我用的是 `file:///…/index.html` 直链（headless），没有真的在资源管理器里双击；URL scheme 相同，但文件关联/默认浏览器差异未覆盖。
3. **OBS 采集本身**：我没有 OBS，无法验证「窗口采集」实际抓到什么、裁剪后是否真的对齐、颜色/缩放是否有偏差。缺陷 2 的 21px 裁切对 OBS 的最终影响是**推断**（板子底部在视口外 ⇒ 采集窗口时看不到那 21px），不是实测。

5. **长时间/高负载稳定性**：没有跑长时间直播（数小时）与内存泄漏观察；没有在低端机/4K 大窗口下测性能。
6. **无障碍与国际化**：未验证键盘 Tab 序、读屏器、对比度。
7. **数据时效性**：数据是 2026-09-30 的快照，与官网一致；**如果官网之后上新英雄/改名，本站不会自动更新**（这是设计如此）。3 位新英雄的分路交叉验证缺失（见 A4）。

9. **`st.applied[]` 的上限/内存行为**：没有测极长对局或反复撤销重做（200 步历史）下的表现。

## 9. 总体判断：这个站点能不能真的拿去直播用？

**能，但请先修掉缺陷 1、2（半小时内的工作量）。**

**可以放心的部分**

- **数据是可信的**：133 位英雄所有可机器比对的字段与官网**零差异**，980 个图片 URL **零死链**，3 个详情页技能文案**逐字一致**。这不是「作者说有 133 个英雄」，而是「我按官网重新核过每个字段」。
- **核心 BP 引擎是稳的**：三种赛制的顺序、回合校验、撤销重做、导出导入、分享码、畸形输入容错，我用真实数据独立跑出 67 项全绿；KPL 20 步与巅峰赛 11 步的边界都对。
- **离线是真实的**：把 CDN 打到 127.0.0.1 后，页面照样操作、照样渲染、零报错、还有 PNG 可截——这一条比大多数「纯静态站」做得扎实。
- **截图是真出图的**：`useCORS:true + allowTaint:false` 配置正确，PNG 1600×900、背景角像素精确匹配、中央大图区有 900+ 种颜色、清空对照组能区分——不是黑图。
- **一键开播的双窗口路径可用**：控制窗操作、展示窗给 OBS，字段级完全一致，开/关/重开/多开都跟得上。
- **窄窗口与多分辨率下按钮都能真的点到**（含 800×900 单列滚动场景，我用真实点击验证）。

**开播前必须处理的两件事**

1. **快捷键双绑定（缺陷 1）**：`空格` 起表无效、`Ctrl+B` 无反应、**`Ctrl+Z` 一次退两步**。直播时按 Ctrl+Z 退错步是最容易出洋相的；在修掉之前，请只用鼠标点「撤销」按钮（按钮路径是单次、正确的）。
2. **展示窗底部缺 21px（缺陷 2）**：常用 16:9 尺寸都溢出，底部计数条会被切。修 `fit()` 或把展示窗窗口开成非 16:9（比如 1440×900 那档就没有溢出）以规避。

**可以接受、但要知道的**

- 截图偶发挂起（缺陷 3）：发生时状态条会一直挂着「正在生成截图…」，重按一次或刷新即可；建议加看门狗。**别把截图当成直播中的关键路径**，它是锦上添花。
- 中央大图快速连点时可能停旧一手（缺陷 4）：人工节奏不会遇到，撤掉「脚本连点」就没问题。

**一句话结论**：**数据与规则达到「可以信任地拿去做直播展示」的水准；交互层还有 1 个高危快捷键缺陷和 1 个中危展示窗裁切缺陷。修掉这两个（都不需要改架构），这个站点就可以直接用于直播。**

### 10.3 缺陷 3（中低）· 截图间歇性挂起 —— ❌ **撤回：这是我自己的探针 bug 造成的误报**

**我的工具错在哪**：`cdp.mjs` 的 `waitFor()` 写成
`if (v !== false && v !== undefined && v !== null && v !== '__ERR') return v;`
本意是「有结果就返回」，但 JS 里 `0 !== false` 是 **true**，所以表达式返回 `0`（"还没有结果"）时它**立刻返回**，根本没有轮询等待。

**证据（同一套 t2b，只改这一个判断）**：

```
修复前: waitFor returned 0 after 99ms
        tr=["h2c-call@3326"]                 ← 只记到「已调用」，没等结果
        toast sequence ["正在生成截图…"] ; shot null
修复后: toast sequence ["正在生成截图…","截图已保存（1600×900 PNG）"]
        PNG 1600×900 / 1.4~1.7MB / 中央区 nonBgRatio 0.72~0.88 / 900+ 色 / 角像素 (5,7,12)
```

也就是说：**点完截图 99ms 就去读结果**（html2canvas 实际需要 ~600ms），读到的当然是「还没出图、状态条还停在『正在生成截图…』、也没有超时提示」——我把这三条误当成了"挂起"。**round 1 报告里"约 13 次调用中 4 次未出图"的 4 次，全部来自这个 bug。** 独立佐证：直接调用 474ms 出图；6/6 抖动探针全出图；受控 trace 三次都是 `h2c-call → h2c-ok(507ms) → toBlob → cb(71ms) → download`。

**lead 据此加的看门狗仍被证明是正确且无害的兜底**（受控实验：把 `html2canvas` 换成永不结算的 Promise）：

```

对照组：真实 html2canvas → downloads=[1290828] 正常出图
```

## 13. round 2 新发现的缺陷

### 缺陷 R2-1（中低）· 赛前面板承接 BP 后，**撤销 / 重开不会回退**，重复点「填充」也清不掉

**复现**：
1. 控制窗打满一局 ranked（双方各 5 pick）；
2. 赛事面板 → 赛前面板 → 点「**立即用 BP 结果填充空位**」→ 采集页正确显示 10 个英雄；
3. 在控制窗按 3 次撤销（draft 只剩蓝 3 / 红 4）；
4. 观察采集页与再次点击该按钮。

**实测**：

```
撤销 3 手后 draft picks = {blue:[孙尚香,刘禅,高渐离], red:[鲁班七号,庄周,阿轲,钟无艳]}
采集页仍显示        = 孙尚香/刘禅/高渐离/孙膑/扁鹊 + 鲁班七号/庄周/阿轲/钟无艳/白起
已不在 BP 里、却仍留在面板上的英雄 = ["孙膑","扁鹊","白起"]
再次点击「立即用 BP 结果填充空位」 → heroIds 完全不变
   （仍为 [111,114,115,118,119,112,113,116,117,120]，三个失效英雄一个都没清）
```

**根因**（`js/story.js:227 applyDraftPicks`）：`if (p.heroId && !force) continue;` —— 非 force 时只补空位；即使 `force=true`，循环里也是「有 pick 就覆盖、没 pick 就 `continue`」，**没有任何清空分支**，所以撤销后多出来的旧 heroId 永远留着。

**影响**：直播中如果 BP 出现改选/回退，赛前面板会**持续显示已经不在 BP 里的英雄**（画面上的错误信息），且 UI 上没有任何办法清掉（只能去手点每个位置的「清空英雄」）。
**建议**：`force=true` 时先整体清空再按 picks 回填；或在 BP 变化时对「由 BP 自动填入」的位置做失效标记（区分"手填"与"BP 自动填"，后者可被覆盖/清空）。

### 缺陷 R2-2（低）· `overlay.html` 的顶部提示条**永远不显示**，里面的两个按钮形同虚设

```
overlay.html?mode=mvp&wzrole=overlay → #displayFlag: display=none, height=0
body classes = "overlay-host overlay-page overlay-mvp"
按钮存在（btnHideFlag / btnDisplayFit 都在 DOM 里）但不可见、点不到
```

**根因**：`.display-flag` 基础样式是 `display:none`，唯一让它显示的选择器是 `styles/main.css:622` 的 `body.role-display .display-flag{display:flex}`——而 `role-display` 只有展示窗（`main.js` 的 `startAsDisplay`）才会加，**采集页没有对应规则**（`overlay.css` 里只有 `.flag-hidden{display:none!important}`，没有显示规则）。

**佐证**：lead 自己的 `shots/overlay-mvp.png` 顶部也没有这条提示条。
**影响**：采集页少了一个「重新适配」的入口（窗口 resize 时仍会自动 fit，所以只是少个手动入口）；另外 `overlay.html` 里「OBS 里裁掉即可，或点『隐藏提示条』」的注释、以及 README 关于采集页提示条的说法与实现不符。
**建议**：给 `body.overlay-page .display-flag { display:flex }`（并让「隐藏提示条」按钮继续可用），或者干脆删掉这段 markup 与注释、README 相应改写。

### 顺带记录（不算缺陷）

- 采集页**不会自动**承接 BP（需要点一次「立即用 BP 结果填充空位」）——按钮是设计内的，但建议 README 明写这一步。
- `overlay.html` 里 `.console-only` 的空态提示（「还没有 MVP 数据…」）在采集页被隐藏、在控制窗可见——与注释一致，正确。
